### Loading state

On first load (no prior data), the page renders a skeleton that mirrors the
real layout: token-slip skeleton (with `perforated-top` / `perforated-bottom`
preserved so the dashed edges stay during loading), a 5-step timeline
skeleton, and a sticky-actions skeleton. `aria-busy="true"` + `aria-live="polite"`
on the main region announces the loading state to screen readers.

### QR code

The token slip's QR is fetched from `/api/v1/qr?data=<tracking URL>` on mount.
The QR lets the customer scan the slip from another device to reopen the
tracking page. The QR fetch is best-effort — on failure the slip renders
its built-in placeholder (same footprint, no layout shift).

### Recent-orders persistence

Each successful poll writes a tiny summary to `localStorage` via
`saveRecentOrder` so `/orders` can list it. The summary contains the token
(the credential itself, already on the device), shop name, order number,
pickup code, total, status, and placedAt ISO timestamp. The
`shopSlug` field is left `null` by the tracking page (the API doesn't expose
it) — `saveRecentOrder`'s merge logic preserves the slug set at placement
time by `CustomerOrderFlowV2.place()`.

### Actions

- **Call shop** — `<a href="tel:...">`, 48px touch target, inline Phone icon.
- **Directions** — opens Google Maps search for `shopName, address` in a new tab (`noopener,noreferrer`).
- **Share order link** — uses `useShare()` hook which calls `navigator.share()` on mobile (Chrome Android, Safari iOS) and falls back to `navigator.clipboard.writeText` on desktop. Surfaces a Toast on success/copied/unsupported.
- **Cancel order** — `SecondaryButton` (de-emphasised per the wireframe), only rendered when `canCancel(status)` returns true (i.e. before printing starts). Uses `window.confirm` to prevent accidental taps. Posts to `/api/v1/o/[token]/cancel`.

### Payment state

The payment card is rendered when the order has a payment OR when the
status is `awaiting_payment` (UTR re-entry after a rejection). States:
- `payment_submitted` (UPI + SUBMITTED) → "Reference XXXX submitted — waiting for the shop to confirm."
- `CONFIRMED` → green check + "Payment confirmed by the shop."
- `REJECTED` → red error + "Enter the correct UTR below, or pay at the counter instead." + UTRInput + Counter-pay button.
- counter_cash / counter_upi pending → "You will pay at the counter when you collect."

When UTR entry is needed (`needsUtr`), the card shows:
1. "Open UPI app to pay" link (uses the `upiIntentUrl` from the API)
2. `<UTRInput>` (12-digit, paste-formatting, completion countdown)
3. `PrimaryButton` "Submit payment reference" (disabled until 12 digits)
4. `TextButton` "Pay at counter instead"

## Notes for the next agent

- The `useTrackPoll` hook is generic (`useTrackPoll<T>`) and lives in `src/lib/hooks/`. Any future page that needs visibility-aware polling with backoff (e.g. a shopkeeper dashboard) can reuse it — the fetcher signature is `() => Promise<FetchResult<T>>` where `FetchResult` is `{ ok, status, data?, message? }`.
- The status-mapping table in `src/lib/customer/order-status-mapping.ts` is the single source of truth for status → pill / timeline / label. If a new backend status is added, update `mapToPill` + `lifecycleIndex` + `statusLabel` there — don't sprinkle `switch` statements across pages.
- The recent-orders localStorage key is `printshop:recent-orders` (capped at 20 entries). The merge logic in `saveRecentOrder` preserves the shop slug when the tracking page writes a status snapshot with `shopSlug: null` — see the docstring there.
- The FAQ accordion uses a CSS grid trick (`grid-rows-[0fr]` → `grid-rows-[1fr]`) for the open/close animation — no animation library dependency. This is the pattern to reuse for any future collapsible region.
- The privacy page is a server component (no `'use client'`) — only static content. It exports `metadata = { title: 'Privacy' }` so the browser tab reads "Privacy · PrintShop SaaS".
