### Key design decisions

**The builder is a peer of `src/lib/payments/upi.ts`**, not a replacement. The server-side builder (`payments/upi.ts`) throws on `amountPaise <= 0` because a real order must have a positive amount. The customer-side builder (`customer/upi-link.ts`) allows `amountPaise = 0` because the customer UI may render a "Pay" button for a zero-rupee token order or a "pay what you want" flow.

**Safety rail**: `buildUpiUri` only accepts the documented parameter shape — there is NO `credentials` parameter, so application secrets can never leak into the URI (verified by test).

**App-specific schemes**: per the brief's instruction "If a scheme can't be verified from official docs, DO NOT ship that button — use the generic `upi://` link only", every app-specific scheme (`tez://`, `phonepe://`, `paytmmp://`, `bhim://`) is marked `verified: false` in the registry. Each entry carries a `source` URL (Google developers, PhonePe developer docs, Paytm docs, NPCI) so a future maintainer can re-verify. The PaymentSheet uses `resolveAppScheme()` which falls back to the generic `upi://` link for any unverified scheme.

**URL encoding**: every parameter is URL-encoded via `URLSearchParams.toString()` (RFC 3986). The brief's specific edge cases are covered by tests:
- Spaces → `+` (verified: no raw whitespace in URI)
- Hindi/Devanagari (`श्री गणेश प्रिंट स्टोर`) → UTF-8 percent-encoded
- Telugu (`శ్రీ గణేష్ ప్రింట్ స్టోర్`) → UTF-8 percent-encoded
- Ampersand (`Shop & Sons`) → `%26` (critical: a raw `&` would split into a new URI param)
- Newlines + control chars + angle brackets stripped from `tn` (they break URI parsing in some UPI apps)
- `tr` is alphanumeric-only (spaces/slashes/ampersands → dashes, runs collapsed, leading/trailing trimmed)

## 2. P8.8 — Offline Queue

### Files created

| Path | Purpose |
|------|---------|
| `src/lib/customer/offline-queue.ts` | localStorage-backed queue + replay engine + Background Sync registration |
| `src/lib/customer/offline-queue.test.ts` | 53 unit tests (jsdom env) covering enqueue/replay/dedup/SSR |
| `src/lib/hooks/use-offline-queue.ts` | React hook with `queue`, `enqueueAction`, `isReplaying` |
| `src/types/native-app.d.ts` | Added `SyncManager` + `ServiceWorkerRegistration.sync` type declarations (lib.dom doesn't ship them yet) |

### Key design decisions

**URL allow-list**: the brief says "ONLY for safe, idempotent actions: submit UTR, cancel order, mark notes" and "NEVER queue order creation or payment initiation silently". This is enforced at enqueue time by `isQueueableUrl()` — three regex patterns match `/api/v1/o/{token}/utr`, `/cancel`, `/note`. Any other URL throws `Refusing to enqueue non-safe action`. Tests verify order-creation (`/api/v1/s/{slug}/orders`) and payment-initiation (`/api/v1/o/{token}/payment`) are both refused.

**Idempotency**: every queued action carries an `id` that doubles as the localStorage dedup key AND the `X-Idempotency-Key` HTTP header sent on replay. Re-enqueuing the same `id` replaces the existing entry (not duplicates). Without an explicit `id`, the queue derives one via FNV-1a hash of `method:url:body` (content-addressed). The server-side dedup is the second layer — a 409 Conflict response is treated as success (the idempotency key was already processed).

**Replay strategy**:
- 2xx → drop from queue
- 409 Conflict → drop (server already processed)
- 4xx (except 408/429) → drop (a bad request won't succeed on retry)
- 5xx / 408 / 429 → retain for next replay (transient)
- Network error → retain for next replay
- `navigator.onLine === false` → skip the replay entirely
- Concurrent `replayQueue()` calls coalesce into a single pass via a module-level `replayInFlight` promise

**Background Sync**: if `navigator.serviceWorker` + `SyncManager` are available (Chromium browsers), `registerBackgroundSync()` registers the `printshop-offline-queue` sync tag. The SW fires `sync` on reconnect even if the tab is closed. iOS Safari (no SyncManager) falls back to the `online` event listener in `useOfflineQueue`.

**Persistence**: localStorage (not IndexedDB) because the queue is small, writes need to be synchronous (a tab close right after enqueue must not drop the action), and the `storage` event gives cross-tab visibility for free.

**SSR safety**: every function guards on `typeof window === 'undefined'`. SSR callers see an empty queue; the hook returns `[]` until mount.

### WCAG contrast verification

Computed via the WCAG 2.x contrast formula on sRGB-linearised luminance (see the verification script reference in `docs/redesign/UPI-MANUAL-TESTS.md` Section 8). All pairs pass AA for their intended use:

| Pair | Ratio | AA status |
|------|-------|-----------|
| Ink (#F7F8FA) on Paper (#0F1B2D) | 16.3:1 | ✓ AA + AAA |
| Muted (#8B97AB) on Paper (#0F1B2D) | 5.9:1 | ✓ AA + AAA-large |
| Cyan (#1A9BD6) on Paper (#0F1B2D) | 5.5:1 | ✓ AA + AAA-large |
| Ink-on-Cyan (#0F1B2D) on Cyan (#1A9BD6) | 5.4:1 | ✓ AA |
| Magenta (#E91E63) on Paper (#0F1B2D) | 3.9:1 | ✓ AA-large (decorative only) |
| Success (#0B7A4B) on Paper (#0F1B2D) | 3.2:1 | ✓ AA-large (status pills) |
| Warning (#F59E0B) on Paper (#0F1B2D) | 8.0:1 | ✓ AA + AAA |

**Critical fix**: white-on-cyan at the brief's specified `#1A9BD6` gives only 3.13:1 — fails AA for normal text. The brief expected ~4.5:1 but the math doesn't support it (the lighter cyan is too luminous for white text). I resolved this by introducing a `--color-on-cyan` token:
- Light mode: white on #006FA6 cyan → 5.6:1 (AA pass)
- Dark mode: ink (#0F1B2D) on #1A9BD6 cyan → 5.4:1 (AA pass)

This keeps the cyan hue consistent across modes while making the PrimaryButton accessible in both. The cyan-as-text-color use (links, accents) still works because cyan-on-paper is 5.5:1 in dark mode.

### FOUC prevention

The existing `next-themes` ThemeProvider in `src/app/layout.tsx` already injects a blocking inline script in `<head>` that reads `localStorage('theme')` + `prefers-color-scheme` and adds the `dark` class to `<html>` BEFORE React hydrates. I verified this by inspecting the rendered HTML:

```
(function(){try{var s=localStorage.getItem('theme')||'system';
var d=s==='dark'||(s==='system'&&window.matchMedia('(prefers-color-scheme: dark)').matches);
...documentElement.classList.add(...)}catch(e){}})("class","theme","system",...)
```

I added a SECOND defensive `<Script id="customer-fouc-prevent" strategy="beforeInteractive">` that sets the `color-scheme` CSS property on `<html>` from the same inputs. next-themes sets the `dark` class but does NOT set `color-scheme`, so without this script the browser's native form controls (scrollbars, date pickers, etc.) would flash light before the CSS catches up. Both scripts run synchronously in `<head>` before hydration — no FOUC.

Verified in the rendered `/dev/ui` HTML: the `customer-fouc-prevent` script ID is present, and `colorScheme` is set correctly.

### Halftone dark mode inversions

Per the brief: "B&W pages: white dots on dark background (invert the dot color)". The `.dark .customer-flow .halftone-bw` selector inverts the radial-gradient dots from `rgb(15 27 45 / 0.2)` (dark ink on white) to `rgb(255 255 255 / 0.22)` (white on dark navy). The `.halftone-bw` class name is unchanged so existing component markup works in both modes.

For colour pages: "Colour pages: magenta stays vivid (already works on dark)". The magenta fill is unchanged; only the cyan/yellow rosette overlay colours are nudged brighter (cyan from 33% → 45% opacity, yellow from 20% → 30%) so the rosette pattern stays visible against the magenta fill in dark mode.

## 6. Notes for the next agent

1. **Server-side idempotency-key dedup is NOT implemented yet.** The offline queue SENDS `X-Idempotency-Key` on every replay, but the route handlers (`/api/v1/o/{token}/utr`, `/cancel`, `/note`) need to CHECK that header and return a cached response (or 409 Conflict) for a duplicate key. Until that server-side dedup is in place, a double-replay (e.g. two tabs both replaying on reconnect) could create a duplicate UTR submission. The queue's localStorage dedup prevents the same tab from double-enqueuing, but cross-tab double-replay needs the server dedup. This is the natural next task (P8.8 server-side companion).

2. **The customer-flow dark mode tokens are scoped to `.dark .customer-flow`** (descendant selector) so they ONLY apply to customer surfaces in dark mode. The shopkeeper/admin portal's own `.dark` block (in `globals.css` line ~330) is untouched. If a future agent wants dark mode on the portal too, they should extend the portal's `.dark` block — do NOT collapse the two scopes.

3. **The `--color-on-cyan` token** is the key to accessible PrimaryButtons in dark mode. White on the lighter dark-mode cyan (#1A9BD6) gives only 3.13:1 (fails AA for normal text); ink-on-cyan gives 5.4:1 (passes). Any future component that puts text on a cyan background should use `text-[var(--color-on-cyan)]`, not `text-white`.

4. **The UPI app-scheme registry** (`UPI_APP_SCHEMES` in `upi-link.ts`) is the single source of truth for which schemes are verified. If a future agent wants to ship a `phonepe://` button, they MUST flip the `verified` flag AND add a passing row in `docs/redesign/UPI-MANUAL-TESTS.md` for that scheme on both Android Chrome and iOS Safari. Code review should reject any `verified: true` change without a corresponding manual-test row.

5. **The `/s/{shopSlug}` page is broken on `main`** due to `ssr: false` in `next/dynamic` (Next.js 16 strictness). This is NOT my regression — it's a pre-existing issue. A separate task should fix `CustomerOrderFlowV2.tsx` (likely by moving the dynamic import into a Client Component wrapper).
