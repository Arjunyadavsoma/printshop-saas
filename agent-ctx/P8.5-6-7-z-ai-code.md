## Architecture Decisions

### P8.5 — Realtime

- **The order token IS the credential**: the server validates the token format
  (32+ hex chars = 128-bit minimum) but does NOT query the DB to verify the
  order exists. Joining room `order:<token>` requires knowing the token, which
  is itself the unguessable credential. This matches the brief's "no separate
  auth" rule + keeps the realtime service DB-free (it's a separate bun
  process).
- **Reconnection is driven by the client**, not socket.io's built-in engine.
  The client calls `socket.connect()` on each backoff tick so it can apply the
  exact schedule (1s → 2s → 5s → 10s → 30s) + trip the polling fallback after
  3 failures. The engine's `reconnection: false` is set to prevent double
  reconnection.
- **The /emit relay now allows `order:*` channels** in addition to `shop:*`.
  This is safe because naming an `order:<token>` room requires the 128-bit
  token — anyone who can name the room already has read access to that
  order's state.
- **Resume sync on reconnect**: the client fetches `GET /api/v1/o/[token]`
  immediately after `connect` fires. The fetched status is routed through the
  same dedup path (`maybeFireStatus`) as socket events, so a status that
  hasn't changed never fires twice (no duplicate toasts).

### P8.6 — OTP

- **The `isRateLimited`/`attemptsRemaining` methods are async** (the brief's
  interface shows them sync, but the cache is inherently async — a sync
  signature would require an in-memory mirror that goes stale across
  instances). The verify response includes `attemptsRemaining` inline, so the
  primary consumer doesn't need a separate call.
- **The plaintext code is NEVER in the response body** + never logged beyond
  the provider's own delivery channel. The `ConsoleOtpProvider` is the single
  place the code exists beyond `crypto.randomInt`, + only fires in dev.
- **Anti-enumeration**: the send endpoint always returns 200 `{ sent: true }`
  regardless of whether the phone is valid / rate-limited / OTP-disabled. The
  verify endpoint returns `{ valid: false, attemptsRemaining: MAX }` for an
  unknown phone (same shape as a fresh code). A locked-out phone returns
  `attemptsRemaining: 0`.
- **The SMS provider is a documented stub**, not a silent no-op. Throwing
  loudly on a misconfigured production deploy is safer than swallowing — the
  customer sees "Could not send code" + the operator sees the error in logs.
- **Feature flag**: `OTP_ENABLED=true` (server) + `NEXT_PUBLIC_OTP_ENABLED=true`
  (client build flag). Both must be set together. When off (default), the
  `/orders` phone-lookup panel shows a disabled "Coming soon" button.

### P8.7 — Resumable Uploads

- **Per-chunk files, not append-only**: switching from a single `.part` file
  (appendFile) to a per-chunk directory (`${chunkDir}/${index}.part`) is what
  enables idempotent re-uploads. A re-upload of the same index overwrites the
  same path with identical bytes — no corruption. The session's in-memory
  `receivedChunks: Map<number, { checksum, size }>` is the authoritative
  record; the chunk files are the durable bytes.
- **Checksum is verified BEFORE writing**: catches transit corruption without
  polluting the chunk dir. A mismatched checksum throws `CHECKSUM_MISMATCH`
  (400) — the client retries the chunk (the bytes were corrupted in transit,
  not on disk).
- **Completion verification is paranoid**: `finishSession` checks (1) the sum
  of received chunk sizes equals `declaredSize`, (2) every expected chunk
  index is present, (3) the assembled bytes' length matches `declaredSize`.
  A mismatch returns 409 `UPLOAD_INCOMPLETE` with a pointer to the status
  endpoint — the client queries status, finds the gaps, + re-uploads only
  the missing chunks.
- **Resume via IndexedDB draft**: the draft snapshot now captures `uploadId`
  + `sizeBytes` + `chunkSize` for files in the `uploading` state. On
  `uploadOne`, the client loads the draft, finds a matching file (by name +
  size), queries `GET /status`, + skips already-uploaded chunks. If the
  session expired (janitor swept it), the client starts fresh.
- **Retry-with-backoff is per-chunk**, not per-upload. A network blip mid-
  upload retries the failing chunk (idempotent — same index + checksum is a
  no-op). 4xx errors that aren't transient (`CHECKSUM_MISMATCH`,
  `CHUNK_CONFLICT`, `FILE_TOO_LARGE`) re-throw immediately.
- **The janitor runs hourly** via Vercel Cron. Sessions older than 1h with no
  recent chunk activity are expired (chunk dir deleted + session removed from
  the registry). The endpoint is idempotent — duplicate runs are safe.

## Non-Goals / Future Work

- **OTP UI for cross-device order list**: the verify endpoint proves the
  phone is real, but the actual "list all orders for this phone" query is a
  separate ticket (needs a `customerPhone` index on the orders table + a
  scoped search endpoint).
- **Real SMS gateway wiring**: the `SmsOtpProvider` is a documented stub.
  Wiring MSG91/Twilio/Gupshup is a one-file change once DLT registration is
  done — see `src/lib/auth/sms-otp-provider.ts` for the checklist.
- **Server-side emit of `order:status` / `order:task` events**: the realtime
  client is wired to receive these events, + the `/emit` relay now allows
  `order:*` channels. The actual emit-side calls (in the order-flow service,
  the print-job status update path, etc.) are a separate ticket — the brief
  scoped this task to the CLIENT + the relay, not the emit-side wiring.
- **WebSocket mini-service restart**: the realtime-service is a separate bun
  process on `:3003`. The system starts it automatically; if it's down, the
  client falls back to polling after 3 failed reconnect attempts (per the
  brief).
