# Document Delivery Architecture

> How print job PDFs travel from the customer's upload to the PrintEXE
> device's local storage. Three delivery modes with automatic fallback.

**Status:** v1.0 — 2025-11-07. Cloud delivery is live; direct + WebRTC
are designed but feature-flagged (awaiting PrintEXE upgrade).

---

## 1. Delivery modes (priority order)

| Priority | Mode | Status | When |
|---|---|---|---|
| 1 | **Direct WebRTC** | 🔒 Feature-flagged (not active) | Both backend + PrintEXE support it (future) |
| 2 | **Cloud staging** | ✅ Live (current) | Agent offline OR direct unavailable |
| 3 | **Polling recovery** | ✅ Live (fallback) | Agent reconnects after downtime |

**Current production behavior:** all delivery is cloud-staged. The PDF is stored in Supabase Storage / R2 / S3. PrintEXE downloads via a presigned URL (15-min TTL).

## 2. The delivery coordinator

**Location:** `src/lib/services/delivery-coordinator.ts`

The coordinator is called when a print job is created (order paid → file enqueued). It:

1. **Finds eligible agents** for the shop (online + heartbeat fresh ≤30s)
2. **Creates a `PrintDeliveryAttempt` record** (tracks the delivery independently from printing)
3. **Publishes `job.dispatch`** via Socket.IO (reaches all connected agents)
4. **If no agent online** → the job stays `queued`; agents poll `GET /agents/jobs/pending`

### 2.1 Agent eligibility

```typescript
const STALE_THRESHOLD_SECONDS = 30;

const eligible = agents.filter(a => {
  if (!a.lastSeenAt) return false;
  const ageSeconds = (Date.now() - a.lastSeenAt.getTime()) / 1000;
  return ageSeconds <= STALE_THRESHOLD_SECONDS;
});
```

### 2.2 Delivery attempt states

| State | Meaning | Transition |
|---|---|---|
| `created` | Attempt record created, not yet dispatched | → `dispatched` |
| `dispatched` | `job.dispatch` event published | → `received` or `failed` or `expired` |
| `received` | PrintEXE acknowledged durable receipt (`POST /agents/jobs/{id}/received`) | → cleanup scheduled |
| `failed` | Delivery failed (checksum mismatch, timeout) | → retry or cloud fallback |
| `expired` | Stale (no receipt within timeout) | → re-dispatch |

### 2.3 Separation of concerns

```
PrintJob.status (printing state):     queued → printing → completed | failed
PrintDeliveryAttempt.status (delivery): created → dispatched → received | failed
FileCleanupTask.status (storage):      pending → completed | failed
```

These are INDEPENDENT. A job can be `received` (PrintEXE has the file) but `printing` (still printing). A job can be `completed` (printing done) while the cloud cleanup is `pending` (not yet deleted).

## 3. Cloud staging (current production flow)

```
Customer uploads PDF
  → POST /api/v1/orders/{id}/files/upload-url (presigned PUT, 5-min TTL)
  → Customer PUTs file to Supabase Storage / R2
  → POST /api/v1/orders/{id}/files (confirm upload + parse page count)
  → PATCH /api/v1/orders/{id}/files/{fileId} (set print options + re-price)
  → POST /api/v1/orders/{id}/checkout (create payment intent)
  → Customer pays via UPI / PhonePe / Paytm
  → Webhook verifies signature + amount
  → Order.status = 'paid'
  → PrintJob rows created (status='queued')
  → Delivery coordinator dispatches:
    → Creates PrintDeliveryAttempt (status='dispatched')
    → Publishes job.dispatch via Socket.IO
    → Agent receives event OR polls /agents/jobs/pending
  → Agent downloads PDF from presigned URL (15-min TTL)
  → Agent calls POST /agents/jobs/{id}/received (durable receipt)
  → Agent calls POST /agents/jobs/{id}/status {status:'printing'} (atomic claim)
  → Agent prints
  → Agent calls POST /agents/jobs/{id}/status {status:'completed'}
  → Server marks file completed, maybe marks order 'ready'
  → Cloud cleanup scheduled (15-min grace period after receipt)
  → Shopkeeper marks order 'collected' → files deleted immediately
```

### 3.1 Presigned URL lifecycle

| URL type | TTL | Generated by | Used by |
|---|---|---|---|
| Upload URL | 5 min | `POST /orders/{id}/files/upload-url` | Customer browser |
| Download URL (agent) | 15 min (900s) | `GET /agents/jobs/pending` | PrintEXE |
| Download URL (shopkeeper) | 60s | `GET /shops/me/orders/{id}/files/{fileId}/print-url` | Shopkeeper browser |
| Receipt download | 15 min | `GET /agents/jobs/pending` | PrintEXE |

If a presigned URL expires before PrintEXE downloads, PrintEXE polls `/agents/jobs/pending` again to get a fresh URL.

## 4. Durable receipt protocol

**Endpoint:** `POST /api/v1/agents/jobs/{jobId}/received`
**Auth:** Device token

**Request:**
```json
{
  "deliveryAttemptId": "uuid (optional, from job.dispatch event)",
  "transferId": "uuid (optional, for future WebRTC)",
  "checksum": "sha256-hex (optional)",
  "fileSize": 123456,
  "receivedAt": "2025-11-07T10:00:00Z"
}
```

**Response 200:**
```json
{
  "success": true,
  "data": {
    "jobId": "...",
    "received": true,
    "cleanupScheduled": true,
    "message": "Receipt acknowledged. Cloud cleanup scheduled for 2025-11-07T10:15:00Z."
  }
}
```

**Idempotent:** duplicate receipts return success without re-scheduling cleanup.

**Purpose:** a successful HTTP download is NOT proof of durable local persistence. PrintEXE must verify:
1. The PDF was fully downloaded (not truncated)
2. The SHA-256 checksum matches (if available)
3. The file was written to local disk
4. The local SQLite queue has the job

Only then should PrintEXE call `/received`. This prevents cloud cleanup from deleting a file that PrintEXE hasn't actually persisted.

## 5. Direct WebRTC transfer (future — feature-flagged)

**Status:** architecture designed, NOT implemented. Requires PrintEXE WebRTC support.

### 5.1 Signaling events (proposed)

| Event | Direction | Payload |
|---|---|---|
| `transfer.offer` | Server → Agent | `{transferId, jobId, fileId, fileSize, checksum, sdp}` |
| `transfer.answer` | Agent → Server | `{transferId, sdp}` |
| `transfer.ice-candidate` | Bidirectional | `{transferId, candidate}` |
| `transfer.started` | Agent → Server | `{transferId}` |
| `transfer.completed` | Agent → Server | `{transferId, checksum}` |
| `transfer.failed` | Agent → Server | `{transferId, error}` |
| `transfer.cancelled` | Server → Agent | `{transferId, reason}` |

### 5.2 Flow

1. Delivery coordinator selects direct mode (both sides support WebRTC)
2. Server creates a `PrintDeliveryAttempt` with `deliveryMode: 'direct'`
3. Server generates WebRTC offer SDP
4. Server publishes `transfer.offer` to the agent via Socket.IO
5. Agent responds with `transfer.answer`
6. ICE candidates exchanged via `transfer.ice-candidate`
7. Peer connection established → PDF transferred directly (no cloud)
8. Agent calls `POST /agents/jobs/{id}/received` with checksum
9. No cloud cleanup needed (file was never in cloud)

### 5.3 Fallback

If WebRTC connection fails (NAT, firewall, timeout):
- `transfer.failed` → coordinator falls back to cloud staging
- Creates a new `PrintDeliveryAttempt` with `deliveryMode: 'cloud'`
- Publishes `job.dispatch` with presigned URL

### 5.4 TURN support

TURN relay server configuration (future):
- `TURN_SERVER_URL` env var
- `TURN_USERNAME` + `TURN_PASSWORD` env vars
- ICE servers passed in the WebRTC offer

## 6. Offline recovery

When PrintEXE reconnects after downtime:

1. PrintEXE calls `POST /agents/token` to refresh its JWT
2. PrintEXE connects to Socket.IO + emits `auth {token: jwt}`
3. PrintEXE polls `GET /agents/jobs/pending` (catches jobs dispatched while offline)
4. For each pending job:
   - Downloads PDF from presigned URL
   - Calls `POST /agents/jobs/{id}/received`
   - Claims via `POST /agents/jobs/{id}/status {status:'printing'}`
   - Prints + completes

### 6.1 Stale job recovery (server-side)

The server's `recoverStaleJobsOnStartup()` (called on container init):
- Finds jobs stuck in `printing` for >5 minutes
- Flips them to `needs_review` (NOT back to `queued` — prevents duplicate printing)
- The shopkeeper manually requeues or completes via the dashboard

## 7. Multi-device support

Multiple PrintEXE devices can be registered per shop:
- `Front Desk PC`, `Printing Room PC`, `Backup PC`

### 7.1 Job dispatch

All connected agents receive the `job.dispatch` event. The first to POST `{status:'printing'}` claims it (atomic conditional update `WHERE status='queued'`). The loser gets `{skipped: true}`.

### 7.2 Future: workload-aware assignment

The delivery coordinator will eventually:
- Track each agent's current job count
- Dispatch to the least-busy agent
- Only notify ONE agent (not all) — reducing noise

**Current behavior (preserved):** all agents are notified. This is simpler + backward compatible.

## 8. Delivery status visibility

### 8.1 Dashboard (shopkeeper)

The dashboard can show delivery status per job:
- **Dispatched** → "Sent to device" (agent notified)
- **Received** → "File received by device" (durable receipt confirmed)
- **Printing** → "Printing in progress" (agent claimed + printing)
- **Completed** → "Printing completed"

### 8.2 Customer tracking

Customer sees (via `GET /orders/{id}/status`):
- `uploading` → "Uploading your document"
- `cloud_staged` → "Securely stored, waiting for shop computer"
- `received` → "Document received by shop"
- `printing` → "Your document is being printed"
- `completed` → "Printing completed"
- `ready` → "Ready for pickup"
- `collected` → "Collected"

**Customer never sees:** delivery mode (direct/cloud), agent name, IP, technical details.

## 9. Error handling

| Scenario | Behavior |
|---|---|
| Agent downloads but doesn't call `/received` | No receipt recorded. Cloud cleanup not scheduled. File stays in cloud. Agent must poll again. |
| Agent calls `/received` but crashes before printing | Receipt recorded. Cleanup scheduled (15 min). Job stays in `printing` → stale recovery flips to `needs_review` after 5 min. |
| Checksum mismatch | Agent should NOT call `/received`. Agent calls `POST /status {status:'failed', lastError:'checksum mismatch'}`. Delivery attempt marked `failed`. |
| Presigned URL expired | Agent polls `/agents/jobs/pending` again. Server mints a fresh URL. |
| Agent offline for >24h | Jobs stay `queued`. No expiry (shopkeeper can cancel). Agent recovers all on reconnect. |
| Duplicate `/received` call | Idempotent — returns success. No duplicate cleanup scheduled. |
