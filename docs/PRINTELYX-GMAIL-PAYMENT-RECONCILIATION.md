The Gmail reconciliation service monitors the connected shopkeeper mailbox for payment notification emails, extracts transaction details, and matches them against pending orders using deterministic rules.\n\n## Monitoring approach: Scheduled polling\n\nThe service uses Gmail search API with a query like 'from:alerts@hdfcbank.net OR from:no-reply@paytm.com OR from:noreply@phonepe.com subject:credit OR subject:received amount' to find payment notification emails. A history cursor tracks the last processed message to avoid re-processing.\n\n## Email filtering\n\nOnly emails from configured sender allowlists are processed. The shopkeeper configures the senders in settings. Common patterns:\n- Bank UPI credit notifications (from:alerts@bank.net)\n- Payment provider notifications (from:no-reply@paytm.com)\n- ToroPay notifications (from:noreply@toropay.co.in)\n\nUnknown senders, forwarded messages, and unauthenticated emails are treated as untrusted and routed to manual review.\n\n## Extraction\n\nThe service extracts: sender, subject, timestamp, transaction reference (UTR/RRN), amount (paise), currency, receiving UPI ID. Only structured fields + the Gmail message ID are stored — no full email bodies.\n\n## Matching rules\n\nA Gmail evidence can auto-confirm a payment ONLY when ALL hold:\n1. Sender is in the allowlist\n2. Amount exactly matches one pending order\n3. Transaction reference (UTR) is present and unique\n4. Receiving UPI ID matches the shop's UPI ID\n5. Exactly one order matches\n6. The email is an incoming credit, not outgoing\n\nOtherwise: routed to manual review (processingStatus = pending).\n\n## Privacy\n\n- No full email bodies stored\n- No email content sent to AI models or third parties\n- Only structured payment fields + message ID retained\n- Shopkeeper can disconnect at any time (tokens revoked, evidence preserved for audit)
