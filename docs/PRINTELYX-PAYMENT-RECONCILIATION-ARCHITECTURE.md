The payment reconciliation engine matches incoming payment evidence against pending orders and confirms payments using deterministic, auditable rules.\n\n## Evidence sources (priority order)\n1. ToroPay signed webhook (payment.confirmed) — trusted, auto-confirms\n2. Provider status API (adapter.verifyPayment) — trusted, auto-confirms\n3. Gmail bank/provider notification — semi-trusted, requires exact match + UTR\n4. Manual shopkeeper confirmation — trusted (shopkeeper assertion)\n\n## Matching pipeline\nEvidence received → normalize → validate source → extract transaction → find candidate orders → verify amount/account/reference → check duplicate → apply rules → confirm or route to manual review\n\n## Auto-confirmation rules (ALL must hold)\n1. Source is trusted (toropay/provider_api/manual) or semi-trusted with UTR (gmail)\n2. Receiving account matches shop's UPI ID\n3. Transaction is incoming credit\n4. Amount EXACTLY matches (integer paise)\n5. Currency matches (INR)\n6. Transaction reference not already used\n7. Exactly ONE pending order matches\n8. Order is in payable status (awaiting_payment/payment_submitted)\n9. Order not already confirmed/refunded\n\n## Safety invariants\n- One transaction reference can only pay one order (DB UNIQUE on PaymentEvidence.transactionRef)\n- One order cannot be confirmed twice (payment state machine + conditional WHERE status)\n- Amount mismatch → rejected, not silently accepted\n- Late events never reverse paid status\n- All actions audit-logged\n\n## Database models\n- ShopGmailConnection: encrypted refresh token, sync cursor, match counts\n- PaymentEvidence: source, transaction ref, amount, status, matched order\n- Both reuse the existing Shop model (FK shopId)\n\n## Reconciliation queue\nThe shopkeeper sees: auto-matched, pending review, unmatched, duplicates, amount mismatches, expired. Uncertain cases are never silently discarded.
