# Realtime + Cross-Invocation State — Production Reality

## TL;DR

Core order processing (creation, token allocation, payment verification,
status transitions, print dispatch) does **NOT** depend on in-memory state
surviving across serverless invocations. All authoritative state lives in
the database.

Two non-critical paths DO use in-memory state on Vercel:
1. Realtime push notifications (`order.paid`, `job.needs_review`,
   `job.queued`/`started`/`completed`) — fire-and-forget. If the realtime
   adapter loses state, the dashboard still updates via 5-second polling.
2. PhonePe/Paytm webhook → order association (`pay:moid:<merchantOrderId>`
   cache entry, 10-minute TTL). If the cache misses, the webhook returns
   404 — the order stays in `awaiting_payment` until the shopkeeper
   manually verifies via `verify-payment`.

The **production-critical path** (UPI deep-link payment + manual
verification) does not depend on the cache, because:
- UPI deep-link has NO server-side webhook. The customer polls
  `GET /api/v1/payments/upi/verify/:orderId`, which reads from the DB.
- Manual verification (`POST /api/v1/shops/me/orders/:id/verify-payment`)
  is shopkeeper-driven and writes directly to the DB.

## Where each piece of state lives

| State                              | Storage     | Survives serverless restart? | Critical for order flow? |
| ---------------------------------- | ----------- | ---------------------------- | ------------------------ |
| Shops, users, orders, files, jobs  | PostgreSQL  | ✓                            | ✓                        |
| `Order.paymentTxnId` (replay guard)| PostgreSQL  | ✓                            | ✓                        |
| `Order.shopId+tokenNumber` unique  | PostgreSQL  | ✓                            | ✓                        |
| `PrintJob_active_file_unique` index | PostgreSQL  | ✓                            | ✓                        |
| `Shop.slug` / `User.email` unique  | PostgreSQL  | ✓                            | ✓                        |
| Rate-limit counters (`rl:scope:ip`)| Cache (mem) | ✗ (per-invocation)           | ✗ (defense-in-depth)     |
| Payment-webhook idempotency key    | Cache (mem) | ✗                            | ✗ (DB UNIQUE is authoritative) |
| PhonePe/Paytm `merchantOrderId` map| Cache (mem) | ✗                            | ⚠ (see below)            |
| Realtime pub/sub channels          | Cache (mem) | ✗                            | ✗ (dashboard polls)      |

## The PhonePe/Paytm webhook cache dependency — explained

When a customer checks out via PhonePe, the checkout route stores a
10-minute cache entry mapping `merchantOrderId → (orderId, shopId, amount,
provider)`. The merchantOrderId is a FRESH UUID generated by the PhonePe
adapter (`crypto.randomUUID()`) — it is NOT the order ID.

When the PhonePe webhook fires, it:
1. Extracts `merchantTransactionId` from the (untrusted) payload.
2. Looks up the cache entry to find the real `orderId`.
3. If cache hit: loads the order + shop, verifies the signature, marks paid.
4. If cache miss: returns 404 ("session expired").

On Vercel with `CACHE_PROVIDER=memory`, the cache is per-Lambda-invocation.
If the checkout and webhook land on DIFFERENT Lambda instances (the common
case under any concurrency), the webhook returns 404. The PhonePe retry
mechanism would re-fire, but if it lands on yet another instance, it also
fails. The order is stuck in `awaiting_payment` until manual verification.

**This is a known, documented limitation for the pilot.** It is NOT a silent
failure — the webhook service logs the 404 with the merchantOrderId, and
the shopkeeper sees the order in their `awaiting_payment` queue with a
"manual verify" action.

**Why this is acceptable for the current release:**
- PhonePe/Paytm sandbox credentials are NOT configured (per the previous
  worklog). The production deployment uses UPI deep-link, which has no
  server-side webhook.
- The shopkeeper's manual verification path is the actual production path,
  and it writes directly to the DB.

**To enable PhonePe/Paytm webhooks in production**, the operator must:
1. Configure Upstash Redis (free tier sufficient for pilot traffic).
2. Set `REDIS_URL`, `REDIS_TOKEN`, `CACHE_PROVIDER=redis` on Vercel.
3. Set `PHONEPE_SALT_KEY` / `PAYTM_MERCHANT_KEY` sandbox credentials, then
   promote to live credentials when ready.
4. (Optional, recommended) Add a DB-backed `PaymentSession` table so the
   merchantOrderId mapping survives even a Redis flush. This is a schema
   change and is NOT in the current release scope.

## Dashboard polling — no realtime dependency

The shopkeeper dashboard (`/shop/dashboard`, `/shop/orders`, `/shop/orders/[id]`)
polls every 5 seconds via `useApiClient`. The poll fetches the orders list
+ payment queue + ready-for-pickup queue from the DB. Even if every
realtime event is lost, the dashboard converges to the correct state
within 5 seconds.

Polling handles API errors gracefully:
- 5xx → keep polling (the dashboard shows stale data with a "reconnecting…"
  indicator).
- 4xx (auth expired) → redirect to login.
- Network error → exponential backoff up to 30s, then keep trying.

The polling interval (5s) is chosen to balance freshness against
Vercel function-execution cost. Under a heavy webhook burst, polling lags
realtime by at most 5s — acceptable for a print-shop queue.

## Duplicate-action safety on the dashboard

The dashboard's quick-action buttons (Verify, Reject, Start, Ready, Cancel)
each fire a single POST. If the user double-clicks:
- The first call transitions the order.
- The second call hits the `canTransitionOrder` guard, which rejects the
  invalid transition (e.g. `paid → paid` is not allowed).
- The UI shows the rejection as a toast, then re-syncs from the poll.

The verify-payment endpoint is additionally idempotent via the
`canTransitionOrder` check — a duplicate verify attempt on an order that's
already `paid` returns an error (not a duplicate side effect).

The webhook's payment mark is protected by the DB UNIQUE constraint on
`paymentTxnId` — a duplicate webhook delivery is caught and treated as
idempotent (no duplicate `paid` transition, no duplicate print dispatch).

## Recommendation for the production release

**Acceptable for authorized production promotion** with the documented
caveat that PhonePe/Paytm webhooks are not reliable on Vercel without
Upstash Redis. The production-critical path (UPI deep-link + manual
verification) is not affected.

**Before enabling PhonePe/Paytm in production**, configure Upstash Redis
(per docs/RATE_LIMITING.md) so the merchantOrderId mapping survives
across Lambda invocations.
