## PAY-001 — Checkout fail-closed verification

### Source verification
- **File:** `src/app/api/v1/orders/[id]/checkout/route.ts`
- **Line 86:** `db.paymentAttempt.create()` — persists attempt
- **Line 100:** `isUniqueConstraintError(e)` — checks for duplicate
- **Line 107:** `throw new Error('Payment attempt could not be persisted')` — ABORTS checkout

**Control flow:** PaymentAttempt creation → if non-unique error → throw → outer catch returns 500

### HTTP test
- **Test:** `fail-closed-verification-tests.test.ts > PAY-001 > checkout returns error when paymentAttempt.create throws`
- **Method:** Mock `db.paymentAttempt.create` to throw `new Error('connection refused')`
- **Result:** `res.status = 500` ✅, `json.success = false` ✅, `json.error.message` contains "persisted" ✅

### Control test
- **Test:** `checkout succeeds when paymentAttempt.create succeeds`
- **Result:** `res.status = 200` ✅, `json.data.merchantOrderId` defined ✅

### Defect discovered: FIND-PAY-001-ORDER (P2)

**The provider (`adapter.createPaymentIntent()`) is contacted at line 42 BEFORE PaymentAttempt is persisted at line 86.** This violates the requirement "persist before provider checkout."

**Impact:** If the provider returns a `merchantOrderId` but PaymentAttempt persistence fails, the checkout aborts (fail-closed ✅) but the provider was already contacted. If the provider times out, no PaymentAttempt is created at all.

**Root cause:** The `merchantOrderId` is generated by the adapter inside `createPaymentIntent()`, and PaymentAttempt needs this ID. Creating the attempt before the adapter call would require either a pre-generated `merchantOrderId` or an adapter interface change.

**Status:** DOCUMENTED — not fixed in this phase (requires adapter interface change).
