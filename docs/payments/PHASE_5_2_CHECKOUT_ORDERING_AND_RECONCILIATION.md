## FIND-PAY-001-ORDER — Fixed: persistence before provider contact

### Original defect
Checkout route called `adapter.createPaymentIntent()` (line 42) BEFORE `paymentAttempt.create()` (line 86). The provider was contacted without a durable PaymentAttempt record.

### Root cause
The `merchantOrderId` was generated by the adapter inside `createPaymentIntent()`. The checkout route needed this ID to create a meaningful PaymentAttempt, so it had to call the adapter first.

### Fix
1. **Generate `merchantOrderId` internally** (line 58 of new checkout route): `const merchantOrderId = crypto.randomUUID()`
2. **Persist PaymentAttempt BEFORE provider contact** (line 66): `await db.paymentAttempt.create({...})`
3. **Pass pre-generated `merchantOrderId` to adapter** (line 92): `adapter.createPaymentIntent({ ..., merchantOrderId })`
4. **All 3 adapters updated** to accept optional `merchantOrderId?: string` and use it instead of generating their own

### Corrected operation sequence
```
1. Authenticate (withOrderAccess)
2. Validate order status + payment eligibility
3. Generate merchantOrderId = crypto.randomUUID()
4. Persist PaymentAttempt (FAIL-CLOSED: abort if fails)
5. Contact provider adapter (ONLY after successful persistence)
6. Cache merchantOrderId → order mapping
7. Return checkout response
```

## Reconciliation strategy

### Documented reconciliation paths

| Scenario | Detection | Recovery |
|---|---|---|
| Attempt with no provider reference | `PaymentAttempt.status='created'` + no `providerTransactionId` | Cron checks age > 10min → mark expired |
| Provider-created intent not linked | Provider webhook arrives with unknown merchantOrderId | `lookupPaymentSession` cache → DB fallback → 404 if not found |
| PaymentEvents stuck in RECEIVED | `processingStatus='received'` + age > 5min | Cron reprocesses (idempotent via unique constraint) |
| Provider-confirmed payment not in orders | `verifyPayment` returns paid but order is `awaiting_payment` | Manual reconciliation: shopkeeper verifies via `/verify-payment` |

### Operational runbook
1. Check `PaymentAttempt` table for stale `status='created'` records (>10 min old)
2. Check `PaymentEvent` table for `processingStatus='received'` records (>5 min old)
3. Check `Order` table for `status='awaiting_payment'` with `paidAt IS NULL` but `paymentTxnId IS NOT NULL`
4. For each: contact provider's status API via `adapter.verifyPayment()`
5. If confirmed paid: transition order via `repos.orders.transitionStatus()`
6. If not paid: leave in `awaiting_payment`, allow retry
