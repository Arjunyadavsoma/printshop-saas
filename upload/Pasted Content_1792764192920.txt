# PrintShop SaaS — Full Website Investigation, Security Audit, Quality Rating & Professional Upgrade

## 1. Role and mission

Act as a principal software architect, senior full-stack engineer, application security auditor, penetration-testing specialist, QA automation engineer, performance engineer, accessibility specialist, and professional UI/UX reviewer.

Your mission is to investigate my existing PrintShop SaaS application in depth, identify every meaningful weakness, explain its root cause, assign a severity and rating, implement appropriate fixes, and raise the quality of the application to a professional production standard.

Do not behave like an assistant that merely suggests improvements. Work directly in the existing repository, inspect the implementation, make justified changes, execute tests, and verify the results.

**Core objective:** transform the existing project from a working prototype or partially verified product into a reliable, secure, maintainable, accessible, and professionally presented SaaS application.

Investigate both code quality and real user experience. A beautiful frontend with insecure APIs is not professional. Passing unit tests without verifying authorization, database behavior, payment flows, and printing reliability is not sufficient.

Do not promise that every possible vulnerability can be found. Report the actual coverage and remaining uncertainty honestly.

# PHASE 3 — Security audit

Use OWASP ASVS and the OWASP Top 10 as reference frameworks. Apply relevant CWE categories when useful.

Assign findings one of these severities:

- **Critical:** credible compromise of the application, sensitive data, or privileged control with severe impact.
- **High:** significant unauthorized access, financial manipulation, data exposure, or security-boundary failure.
- **Medium:** meaningful but more constrained security or integrity risk.
- **Low:** limited-impact weakness or defense-in-depth gap.
- **Informational:** hardening recommendation or observation without a demonstrated vulnerability.

For every finding, include evidence, affected files or routes, impact, reproducibility in an authorized environment, recommended remediation, and verification status.

## 3.1 Authentication and sessions

Inspect:

- Registration and login
- Password hashing and verification
- Password reset and account recovery, if implemented
- JWT creation, validation, expiry, and signing algorithms
- Refresh-token rotation and revocation
- Cookie flags, where cookies are used
- Token storage and leakage risks
- Logout behavior
- Brute-force and credential-stuffing protection
- Account enumeration
- Role assignment
- Session invalidation
- Password and token logging
- Authentication on every protected route

Verify that authorization cannot be bypassed by calling APIs directly.

Do not assume JWT use automatically makes authentication secure.

## 3.2 Authorization and multi-tenancy

Treat tenant isolation as a high-priority audit area.

Test whether a shopkeeper can access another shop's:

- Orders
- Uploaded files
- Print jobs
- Printer settings
- Payments
- Reports
- Audit records
- User records

Inspect object-level authorization, insecure direct object references, role checks, administrator access, and repository queries.

Ensure ownership checks happen on the server and are applied consistently to nested resources.

Use two or more test tenants to verify isolation.

## 3.3 File uploads and document processing

Inspect:

- File type validation
- MIME-type spoofing
- File signature validation
- Filename handling
- Upload limits
- Storage permissions
- Public versus private buckets
- Signed URL expiration
- Unauthorized file downloads
- Path traversal
- PDF parser safety
- Malformed and password-protected documents
- Large-file denial of service
- Temporary-file cleanup
- Document retention and deletion
- Cross-tenant access
- File processing timeouts

Treat uploaded files as untrusted input.

Never rely solely on a filename extension or browser-provided MIME type.

Ensure private documents are not accidentally exposed through public storage, logs, cached responses, or predictable URLs.

## 3.4 Payments and financial integrity

Inspect all UPI payment and verification flows.

Check whether:

- Client requests can manipulate amounts
- UTRs or screenshots are incorrectly treated as verified payments
- Payment callbacks or webhooks are authenticated
- Duplicate callbacks are idempotent
- Repeated requests create duplicate payment records
- An order can be marked paid without authorization
- Refund states are fabricated or inconsistent
- Order totals and collected amounts are conflated
- Currency rounding is consistent
- Cancellation and payment transitions are safe
- Cash collections are explicitly recorded
- Reports count only the correct financial states

Use integer paise for monetary calculations where applicable.

Never claim that a payment is provider-verified unless the implemented verification mechanism establishes that fact.

## 3.5 API and input validation

Inspect:

- Every API route
- Request schemas
- Query parameters
- Route parameters
- JSON parsing
- Body-size limits
- Error responses
- HTTP methods and status codes
- Rate limiting
- Pagination limits
- Database query construction
- Sensitive response fields
- Excessive resource consumption
- Cross-origin behavior
- CSRF exposure where relevant
- Caching of authenticated responses

Verify that malformed input fails safely and that API responses do not disclose secrets, internal stack traces, or unrelated tenant data.

Do not introduce permissive CORS policies or trust Origin headers as the sole authorization mechanism.

## 3.6 Printing security

Inspect both PrintLatch and native Windows printing paths.

Verify:

- Pairing and token handling
- Localhost service authentication
- Origin and Host validation
- DNS-rebinding protections
- Arbitrary URL prevention
- Arbitrary file-path prevention
- Printer-name validation
- PDF authorization
- Request and file-size limits
- Job status authorization
- Duplicate submission protection
- Cross-engine fallback behavior
- Uncertain job reconciliation
- Audit logs
- Temporary-file cleanup

The local native service must not expose arbitrary filesystem access or command execution.

Do not blindly retry a job whose physical outcome is uncertain.

Do not equate successful submission with confirmed physical completion.

Do not claim duplex support works on a particular printer without validating its driver and physical output.

## 3.7 Secrets and configuration

Inspect:

- `.env` files and environment-variable usage
- `.gitignore`
- Committed configuration
- Client-exposed environment variables
- Logging
- Error messages
- Build artifacts
- CI configuration
- Git history where available and authorized
- Third-party API credentials

Never print secret values in the report.

If a credential appears exposed, identify the type and location without reproducing the value. Recommend revocation and rotation. Do not rotate production secrets automatically.

## 3.8 Security headers and browser behavior

Inspect and verify where appropriate:

- Content Security Policy
- HSTS
- X-Content-Type-Options
- Referrer-Policy
- Frame restrictions
- Permissions-Policy
- Secure cookie settings
- Cache-Control on private data
- Open redirects
- Clickjacking
- XSS risks
- CSRF risks
- Unsafe external links

Do not apply a restrictive CSP blindly if it breaks required functionality. Test the policy against the actual application.

# PHASE 12 — Remediation and implementation

After the initial investigation, build a prioritized remediation backlog.

For every finding, record:

- ID
- Severity
- Category
- Affected file or route
- Evidence
- Root cause
- User or business impact
- Recommended fix
- Regression test
- Status
- Verification evidence

Prioritize in this order:

1. Critical security vulnerabilities and data exposure
2. High-severity authorization, payment, and tenant-isolation defects
3. Data loss, duplicate payments, duplicate printing, and incorrect business state
4. Broken core customer or shopkeeper workflows
5. Medium-severity security and reliability issues
6. Accessibility and major UI/UX problems
7. Performance bottlenecks supported by measurements
8. Maintainability improvements
9. Low-risk visual polish

Implement fixes in small, reviewable batches.

After each batch:

1. Inspect the diff.
2. Run the relevant regression tests.
3. Run type-check and lint.
4. Run the production build when practical.
5. Check for accidental changes to unrelated behavior.
6. Update the remediation report.

If a change requires a production migration, new secret, unavailable external service, or hardware test, prepare the change and document the remaining manual step rather than pretending it has been completed.

Do not stop after producing the backlog. Continue fixing issues until all safe, authorized, high-priority work has been addressed or a clearly documented blocker is reached.
